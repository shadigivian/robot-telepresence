# Shared status icons and tooltips

The status presentation is shared across Boss monitoring/overview, organization robot management/status, Fleet inventory and detail dialogs, session/control views and history, public organization robot listings, support tickets and matching navigation. Notifications and empty-state illustrations continue to use the existing shared Feedar assets. Event content, headings, real user names/usernames, battery percentages and timestamps remain visible. Organization logos, maps, QR codes, streams and brand artwork are unchanged.

`StatusIndicator` renders the status glyph with its explanation in `StatusTooltip`. Use `showText` only for essential values, such as identity or percentage. Current user and last user always use their corresponding asset, including empty states. `TicketStatusIndicator` uses the common ticket glyph and human-readable status mapping (`new` and `open` both explain Open); its information button is named Explain ticket state to avoid colliding with the actual Open action or the Ticket status select. `sessionStatusIconName` and `activityIconName` centralize presentation mapping.

Activity follows the existing `robotControlStatus` selector: Idle, Working · telepresence and Working · mission. Four canonical SVGs and the matching `ActivityIcon` component provide pause, camera, route and neutral overview glyphs. They use currentColor, the existing 24-unit grid and 1.85 stroke, without text, letters, numbers in the artwork, foreignObject or animation. No new runtime state was added. A configured telepresence mode is described as a mode, not inferred to be an active call.

The information control opens a real tooltip on hover and keyboard focus. Tap/click pins it; a second tap, outside pointer, Escape or blur dismisses it. The bubble remains hoverable. It uses a portal into the nearest open native dialog or document body and the native popover top layer; viewport clamping and scroll/resize observers keep it outside table clipping. Buttons have accessible names and decorative SVGs. `passive` mode belongs inside an existing action: it adds no nested button or intercepted activation, and focusing that action shows one combined description that updates when its statuses change. Mobile status descriptions are also available on the status information controls and in the robot detail view. Visual targets stay compact; coarse-pointer hit areas are enlarged without forcing tall table rows. Battery values remain on one line while identities may wrap.

Domain models, provider/service code, permission policy, battery thresholds, session/grant lifecycle, TTL and simulation handlers were not changed. The original sixteen SVG asset files retain their source hashes.

Typecheck, lint, 100 unit tests, build and two static base-path checks passed before the final battery-only CSS adjustment; final gate logs in the accompanying evidence record their repeat on the delivered source. The complete 54-case E2E run passed 53 and failed one central-support assertion: the reply text matched both the posted paragraph and the textarea before its draft cleared. That test and reply handler were left unchanged. A separate run also encountered a login/bootstrap wrong-route failure; its root cause remains unresolved. Neither result establishes that historical remote CI is fixed.

After the final battery wrapping fix, all nine related status/asset E2E cases passed, including all five new cases; the added geometry check verifies the digits and percent sign share one rendered line. An earlier first version incorrectly counted DOM Range fragments as lines and failed; that result is retained, and the check now compares fragment top/bottom coordinates. No test was skipped and no timeout increased. Two existing presentation tests were updated to assert the correct Current User glyph and focusable tooltip semantics; action, reply and permission assertions remain.

The external E2E configuration imports the app configuration and changes only the dedicated local port to 5185 and web-server ownership. It uses one worker and zero retries, with original test timeouts. A prestarted official Vite avoids the previously observed Windows runner cleanup barrier. It is not a deployment test. Actual screenshots, route coverage, all attempts and exact file hashes are in the separate delivery evidence. No VPS, physical robot, remote deployment or server revision was verified.
